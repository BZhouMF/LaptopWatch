一、架构评估
================================================================================

【亮点】

1. 多模式架构设计清晰
   - Normal / Video / Image / Douyin / Category 五种模式通过 RUN_MODE 统一切换
   - 蓝图按职责拆分：auth / core / normal_api / media_api / douyin_api / category_api / file_api
   - require_mode 装饰器做模式隔离，不会出现跨模式接口误用

2. DB + 文件系统双轨策略合理
   - SQLite 的 nodes + media 两张表缓存文件系统元数据
   - sync_folder() 增量同步设计精巧：对比 fs mtime/size/type 只更新变化条目
   - DB 不可用时 Fallback 到 os.scandir 直接读文件系统

3. 双视频服务器架构正确
   - Flask (waitress) 处理页面 + API + 鉴权
   - FastAPI (uvicorn) 独立线程处理大文件流式传输
   - 避免了 Flask 同步阻塞影响视频流体验

4. MediaPlayerPage 双缓冲视频播放器实现专业
   - A/B video element 交替使用，避免切换时的黑屏/重新加载
   - canplay 事件驱动 + 400ms/1500ms 双重 fallback 容错
   - 手势系统设计完整：滑屏/seek/音量/亮度/长按加速
   - 预加载下一视频（douyin 模式）

5. 进程生命周期管理考虑周全
   - gui.py + qid.py 双入口，互相兼容
   - force_kill_port 考虑了 reloader 子进程、TIME_WAIT、父进程树杀
   - atexit 注册兜底清理

6. 路径穿越保护
   - serve_media / thumbnail / category 都有 resolve() + startswith 校验

【架构隐患】

1. 三个独立进程（Flask 5002 + FastAPI 5003 + QID 5001）
   - 启动/停止逻辑分散在 gui.py 和 qid.py 中各自实现
   - 没有统一的进程编排层
   - 端口号硬编码在多个文件中（5001/5002/5003）

2. DB_PATH 命名策略隐式依赖 MEDIA_DIR 的 basename
   - config.py 注释提到 "DB_PATH 以 MEDIA_DIR 的 basename 命名"
   - 但实际代码中只有一个固定路径 db_path/laptopwatch.db
   - 不同媒体目录共享同一个 DB，切换目录时旧数据不会清理

3. sync_folder 调用分散在 7 个不同位置
   - media_api._db_load_more
   - douyin_api._ensure_media_synced
   - db_utils.traverse_media
   - media_utils.get_files_in_folder
   - media_utils.get_category_children_info
   - category_api.category_data
   - category_api.category_grid_more
   - 没有统一的"同步调度器"，容易漏同步或重复同步

二、数据完整性 Bug（P0 - 阻断发布）
================================================================================

Bug #1: 随机模式和抖音模式深层文件夹文件不可见
-------------------------------------------------
文件：blueprints/media_api.py:61-64, blueprints/douyin_api.py:37-41
原因：_db_load_more(is_random=True) 和 _ensure_media_synced() 都只调用
      sync_folder(conn, str(config.MEDIA_DIR)) 同步根目录 1 层。
      但后续 SQL 查询的是整个 media 表（WHERE m.path LIKE media_prefix + '%'），
      二级、三级子文件夹从未被 sync_folder 覆盖，其文件不在 media 表中。
影响：全新部署直接开随机模式或抖音模式 → 大量文件丢失
复现：删除 DB 文件 → 启动 douyin 模式 → 只能看到 MEDIA_DIR 根目录下的视频
修复：启动时用后台线程调用 traverse_media 做全量同步，或在随机/抖音初始化时
      增加"发现子文件夹"的扫描逻辑

Bug #2: 非随机模式不知道总数，翻页依赖 has_more
-------------------------------------------------
文件：blueprints/media_api.py:109-111
原因：traverse_media 只返回 data/next_offset/has_more，不返回 total
影响：前端 MediaGrid 无法显示总页数，用户只能一页页翻不知道还有多少
修复：traverse_media 预先做一次轻量 COUNT 查询（只遍历文件夹结构不算文件），
      或者用 get_media_page(count_total=True) 先拿总数

Bug #3: douyin_history 存在 Flask session 中可能超 4KB 限制
-------------------------------------------------
文件：blueprints/douyin_api.py:14-25
原因：每条视频路径 + pickle 序列化开销，200 条可能超过浏览器 cookie 4KB 限制
影响：session cookie 截断 → 历史丢失 → 视频可能重复播放
修复：将历史迁移到 DB（douyin_history 表）或 localStorage

Bug #4: 切换 MEDIA_DIR 时旧 media 表数据不清理
-------------------------------------------------
文件：config.py:191-196, utils/db_utils.py:48
原因：DB_PATH 固定为 db_path/laptopwatch.db，切换媒体目录后旧目录的 media
      记录仍然存在，新旧数据混在一起
影响：旧目录的文件出现在新目录的文件列表中（如果 path 格式巧合匹配）
修复：切换媒体目录时清空 media 表并重新全量同步

四、内存管理问题（P1）
================================================================================

问题 #1: _random_id_cache 内存占用不可控
-----------------------------------------
文件：blueprints/media_api.py:38-39
_MAX_RANDOM_CACHE_ENTRIES = 10，但每个条目存储了完整的 all_ids 列表。
在 100 万文件的媒体库中，每个条目约 8MB（100 万个 Python int 对象）。
10 条 → 80MB，在 2GB 内存的 NAS/旧笔记本上可能触发 OOM。

修复：不要缓存完整的 shuffled ID 列表，改为缓存 seed 值 + 用 SQL OFFSET 翻页。
      或者用 Python array('Q') 代替 list[int] 减少内存占用。

问题 #2: _category_info_cache 无限增长
---------------------------------------
文件：utils/media_utils.py:103
没有条目上限，没有 TTL，没有定期清理。
每浏览一个新的文件夹路径就增加一条，在深层目录树中可能积累数百条。

修复：加 LRU 上限（如 100 条），或者基于文件夹路径层级限制缓存数量。

问题 #3: CacheManager._thumbnail_cache 无上限
----------------------------------------------
文件：utils/cache_utils.py:27, cache_utils.py:100-106
内存中的 base64 缩略图缓存没有条目数限制，与 DB cover BLOB + 文件系统缓存
三重存储同一份缩略图数据。

修复：既然 DB 已有 cover BLOB，_thumbnail_cache 可以完全移除或设置很小上限
      （如最近 50 张）。当前 DB cover + 内存缓存两者其一即可。

问题 #4: 封面数据三重冗余存储
---------------------------
同一张图片的缩略图被存储了三次：
  1. DB media.cover BLOB（_upsert_media 预生成）
  2. generate_and_cache_cover 的 ON CONFLICT UPDATE（实时生成时再次写入）
  3. CacheManager._thumbnail_cache 的 base64（前端请求时再缓存）

对 10 万张图片的媒体库，仅 cover BLOB 就可能占用 2-5GB（每张 20-50KB JPEG）。

修复：统一封面缓存策略——DB BLOB 作为唯一持久化层，去掉内存 base64 缓存。
      或者反过来：不存 DB BLOB，纯内存 LRU 缓存 + 文件系统 .thumbnail 目录。

问题 #5: preview_cache 无自动清理
---------------------------------
文件：utils/cache_utils.py:30
preview_cache 只在 log_access 中调用 clean_preview_cache(3600) 清理。
但如果用户长时间不断浏览，preview_cache 的 key tuples 持续增长，
因为清理只在每次 API 调用时被动触发。

修复：在 CacheManager 中增加定时清理线程，或改用 LRU 策略。

五、数据库设计问题（P1）
================================================================================

问题 #1: media 表无 cover 生成状态字段
--------------------------------------
当前 design：cover IS NULL 表示"未生成"。无法区分"生成失败"和"尚未尝试生成"。
如果某个文件 cover 生成失败（文件损坏/格式不支持），每次请求缩略图
都会重新尝试实时生成，浪费 CPU。

修复：加 cover_status 列（0=未生成, 1=已生成, 2=生成失败），失败的不再重试。

问题 #2: 没有文件哈希
--------------------
nodes 和 media 表只用 mtime + size 判断文件是否变化。
如果文件内容变了但 mtime 和 size 不变（极少但可能），DB 不会感知。
而且无法做去重检测。

修复：可选——加 file_hash 列（SHA256 前 16 字节），用于去重和精确变更检测。

问题 #3: 没有外键约束
---------------------
SQLite 默认关闭外键。media.parent_id 和 nodes.parent_id 没有 FOREIGN KEY 约束。
如果有 bug 导致孤立的 media 记录，不会报错。

修复：conn.execute("PRAGMA foreign_keys=ON")，或者在清理逻辑中增加一致性校验。

问题 #4: WAL 模式在测试中可能残留
--------------------------------
CLAUDE.md 提到 "config.DB_PATH 以 MEDIA_DIR 的 basename 命名数据库"，
测试用临时目录产生大量 tmp*.db 残留，需要手动清理。
说明测试隔离不够好——每个测试应该用 :memory: 或独立的临时 DB。

六、前端问题（P1）
================================================================================

问题 #1: 错误的 401 处理导致无限重定向循环
----------------------------------------
文件：react/src/api/client.ts:15-20
401 拦截器跳转到 /login?redirect=...，但如果 /login 页面自身也因为
某些原因返回 401（如 session 检查 API），会形成循环。

ProtectedRoute 和 LoginPage 都调用 /api/check_path 验证状态，
如果这个 API 也返回 401，拦截器会再次触发 redirect。

修复：在拦截器中加防护——如果当前已在 /login 页面，不再重定向。

问题 #2: CategoryBrowsePage 的 sessionStorage 栈可能不一致
--------------------------------------------------------
文件：react/src/pages/CategoryBrowsePage.tsx:132-134
sessionStorage 保存了整个 NavEntry 数组（含 page_cache 含 MediaItem 数据）。
在深层浏览中，这个数组可能达到 MB 级别，sessionStorage 通常限制 5MB。

修复：只保存必要的导航元数据（路径 + 索引），不保存页面数据。

问题 #3: 前端 useCallback 依赖爆炸
----------------------------------
MediaPlayerPage 有 50+ 个 useCallback/useRef/useEffect，state_ref 和 ref
之间的同步靠 15+ 个 useEffect 做 "Sync refs"。维护成本极高，
新增一个状态变量可能需要改 3 个地方。

修复：考虑用 useReducer 统一管理播放器状态，减少 ref 同步的需要。
      或者抽取 custom hook usePlayerState 封装复杂度。

问题 #4: BrowsePage 的文件夹加载和文件加载是串行的
-------------------------------------------------
文件：react/src/pages/BrowsePage.tsx:152-191
先 await folder_resp，再 await file_resp。
后端 /api/list 的两个请求之间没有依赖关系，应该并行。

修复：用 Promise.all 并行请求。

问题 #5: 缩略图 onError 隐藏了 img 标签但用户不知道原因
-----------------------------------------------------
MediaGrid.tsx:171-173, CategoryBrowsePage.tsx:79:
    onError={(e) => { (e.target as HTMLImageElement).style.display = "none"; }}
图片加载失败完全静默。用户看不到任何占位符，不知道是封面未生成还是网络错误。

修复：onError 时显示一个默认占位图标（如 🎬/🖼️ emoji），让用户知道这里有内容。

问题 #6: 移动端体验未充分测试
----------------------------
- BrowsePage 的 IntersectionObserver 无限滚动在移动端可能触发过早/过频
- MediaPlayerPage 的手势系统只处理了 TouchEvent 但 mouse 事件在移动端无意义
- 没有响应式设计针对不同屏幕宽度的测试覆盖

七、安全与配置问题（P2）
================================================================================

问题 #1: 硬编码默认密码
-----------------------
config.py:144: DEFAULT_PASSWORD = '574406731'
auth.py:179: 以 config.DEFAULT_PASSWORD 明文比较
qid.py:96, qid.py:671: 使用 DEFAULT_PASSWORD 认证

密码在源码中可见，Git 历史中永久保留。
虽然这是个人 LAN 工具，但如果发布出去任何人都能通过读源码获得管理权限。

修复：首次启动时生成随机密码并强制用户记录，或者读取环境变量不允许默认值。

问题 #2: /register 是陷阱，但 /login 是真实入口
----------------------------------------------
auth.py:114-144: 注册页面触发陷阱关闭所有服务。
但攻击者可以直接暴力破解 /login。

修复：加登录失败次数限制（如 5 次/分钟/IP），存在 DB 中而非内存。

问题 #3: SERVICE_ACTIVE 安全模型薄弱
------------------------------------
app.py:96-102: SERVICE_ACTIVE=False 时拦截大部分请求返回 503。
但白名单路径 /media/serve_media/ 被 _GATE_SKIP_PREFIXES 跳过（app.py:76-77），
意味着未激活状态下仍可访问媒体文件。

修复：SERVICE_ACTIVE gate 应该在 before_request 的最前面，或在 require_mode 中
      也检查 SERVICE_ACTIVE。

问题 #4: X-Auth-Password 头部明文传输
-------------------------------------
gui.py:418, core.py:179: 通过 HTTP Header 传递密码。
虽然是 localhost 通信，但如果 LAN 上有人抓包可以看到密码。

修复：localhost 场景可接受，但应加注释说明仅限本地通信使用。

十、优化建议汇总
================================================================================

性能优化：
  1. 视频封面预生成后台线程——用线程池批量提取视频中间帧，低优先级不阻塞 UI
  2. traverse_media 加 COUNT 预查询——先轻量 SElECT COUNT(*) 拿到总数
  3. sync_folder 批量 upsert——用 executemany 替代逐条 INSERT
  4. 前端缩略图请求加 HTTP/2 Server Push 或懒加载占位符

架构优化：
  5. 统一"同步调度器"——一个 SyncCoordinator 类管理所有 sync_folder 调用
  6. 合并 cover 生成逻辑——一个 cover_service.py 提供统一的封面生成/缓存
  7. 抽取 usePlayerState hook——减少 MediaPlayerPage 的 ref 同步复杂度
  8. 加后台预扫描——服务启动时后台 os.walk 全量填充 DB，前端只查 DB

体验优化：
  9. 非随机模式显示"正在统计..."然后异步拿到 total
  10. 抖音模式滚动到底时提前预取（已有 preload_next，但可以更激进）
  11. 缩略图加载失败显示默认占位符而非完全隐藏
  12. 增加骨架屏（skeleton screen）替代纯 spinner

十一、修复优先级路线图
================================================================================

P0 - 阻断发布（有则不能发）：
  1. 随机/抖音模式深层文件夹文件不可见 → 启动时全量预扫描
  2. 关键路径静默吞异常 → 全部加 logger.error + 返回错误 JSON
  3. DB 路径固定导致切换目录数据不隔离 → 切换时清理 + 全量同步

P1 - 严重影响体验：
  4. 内存缓存加 TTL + 上限 → CacheManager 改造
  5. 封面三重冗余存储 → 统一为 DB BLOB 唯一持久化层
  6. non-random 模式无总数 → traverse_media 加 COUNT
  7. douyin_history 从 session 迁移到 DB
  8. 前端 401 循环重定向 → 加防护
  9. CategoryBrowsePage sessionStorage 溢出 → 精简存储

P2 - 打磨：
  10. 密码首次启动强制设置，去掉硬编码
  11. 硬编码端口号集中到 config.py
  12. 统一三处封面生成逻辑
  13. 补全关键路径集成测试（smoke test）
  14. 缩略图加载失败的友好降级 UI
  15. 增加数据库 WAL checkpoint 定期执行

================================================================================
总体评价
================================================================================

代码骨架扎实，功能覆盖全面（5 种运行模式、3 个服务进程、双缓冲播放器、
手势系统、SSR 目录浏览、定时关机、管理面板）。作为个人 LAN 工具已经
超过同类项目的水准。

但要作为可发布的正式产品，核心问题是：
  1. 数据完整性——随机/抖音模式下深层文件不可见是功能级 bug
  2. 弹性不足——异常处理大面积静默、内存管理缺乏上限
  3. 覆盖边界清晰——为"家庭 NAS 几百个文件"场景设计，
     但没考虑"8TB 硬盘 500 万文件"的极端场景

如果 P0 三条修掉 + P1 的内存和封面路径优化，这是一个可以放心推荐
给朋友使用的 LAN 媒体服务器。
